# Bug log

Every bug found while building MLSChat, with the tool that found it. Bugs in the test harness
and the measurement code are listed too, because a wrong harness produces wrong numbers.

The protocol code itself passed the official vectors on their first full run, so the vector
suite did not find bugs in it. The entries below are what the other tools found.

| # | Area | Bug | Found by | Fix |
| --- | --- | --- | --- | --- |
| 1 | differential harness | After a Remove, the session indexed `members[committer]` to count who committed, but the removal had shifted the vector, so the index could be out of range (panic at `differential/src/lib.rs:389`) | the first 15-session OpenMLS differential run | record whether the committer is MLSChat or OpenMLS before applying the operation |
| 2 | exp1 metric | "parents filled" counted every parent with any member below it. A parent whose other subtree is empty is never on anyone's filtered direct path, so RFC 9420 leaves it blank; the metric reported 99/102 for a tree that was in fact full | reading the exp1 smoke-run output | count only parents with members under both children; the steady-state tree is then 9,999/9,999 at n = 10,000 |
| 3 | build | Running `cargo test -p client` alone unified Cargo features differently from the workspace build and silently started a second 20-minute RocksDB compile | watching the process list during a stuck test | always build and test at workspace scope (`--workspace --exclude web`) |
| 4 | experiment orchestration | A background exp1 launch that looked failed was only waiting on Cargo's build lock; a second launch then ran concurrently, so two runs contended for 2 vCPUs and appended to the same results file | process list showed two `exp1_membership` processes | killed both, deleted the results file, reran one; logs now go to `$MLS_WORK/logs`, not `/tmp` |
| 5 | TLA+ model | The first configuration (3 clients, 2 commits each, no symmetry) had not finished after 9.4 million distinct states | TLC progress output | client symmetry set and one commit per client in the main configs, plus a 2-client, 2-commit config; all now finish |
| 6 | mls library (performance) | Every commit built and signed a GroupInfo carrying the whole ratchet tree, even when no Welcome was sent. That made a Remove commit O(n): 20 ms at 5,000 members and 41 ms at 10,000, doubling with the group, where TreeKEM should be logarithmic | exp1: committer time doubled from n = 5,000 to n = 10,000 (`results/exp1_membership_v1_eager_groupinfo.jsonl`) | build the GroupInfo only when a Welcome needs it; Remove at 10,000 members fell to 4.64 ms (`results/exp1_membership.jsonl`) |
| 7 | client | Publishing a key package is fire-and-forget on the publisher's connection, so another client's fetch on a different connection could reach the server first and find nothing ("no key package for t7-new0") | exp3, trial 7 of the fenced concurrent-add runs | `fetch_key_package` retries with a short backoff before failing |
| 8 | delivery service and client (ordering) | A client that fell behind could send an application message built on an epoch the server no longer accepted. The server rejected it as too old, the client re-encrypted and resent it, and by then a later message from the same sender had already been logged, so 16 messages (240 delivery events) reached receivers out of their sender's order | exp4 chaos run, 16 clients x 1,000 messages, 49 server kills (`results/exp4_chaos_v1_before_sender_seq.jsonl`) | per-sender sequence numbers on application messages: the server accepts only the sender's next number, the client resends in order after an `OutOfOrder` reply and re-encrypts a too-old message (same number) only after catching up. Rerun: 0 reordered of 496,800 deliveries across four runs (`results/exp4_chaos.jsonl`) |
